# DAAM — Terraform Deployment Guide

This directory contains the Terraform configuration used to provision and bootstrap the DAAM application on AWS.

The goal of this document is to make the deployment reproducible for any developer who has:

- an AWS account,
- access to the `nuriyevn/daam-dis` GitHub repository,
- a GitHub Deploy Key for that repository,
- Terraform installed locally,
- and the corresponding AWS credentials configured.

---

## 1. What Terraform creates

The current Terraform configuration provisions:

- AWS EC2 instance
- Amazon Linux 2023
- `t3.micro` instance type
- 30 GB encrypted `gp3` root volume
- SSH key pair generated by Terraform
- Security Group
- Elastic IP
- Nginx
- Git
- Node.js 20
- npm
- the DAAM GitHub repository
- the `codebase` Git branch
- project dependencies via `npm run setup`

The application source is cloned directly from GitHub on the EC2 instance.

Current AWS region:

```text
ap-south-1
```

Current application branch:

```text
codebase
```

# 4. GitHub Deploy Key

The EC2 server needs read access to the private GitHub repository.

A GitHub Deploy Key allows the EC2 instance to authenticate to GitHub using SSH.

## 4.1 Generate a deploy key

On the deployment computer:

```bash
ssh-keygen -t ed25519 -C "daam-ec2-deploy" -f ~/.ssh/daam_ec2_deploy
```

This creates:

```text
~/.ssh/daam_ec2_deploy
~/.ssh/daam_ec2_deploy.pub
```

The `.pub` file is the public key.

The file without `.pub` is the private key.

**Never commit the private key to Git.**

---

## 4.2 Add the public key to GitHub

Open the repository:

```text
https://github.com/nuriyevn/daam-dis
```

Go to:

```text
Settings
→ Deploy keys
→ Add deploy key
```

Use:

```text
Title:
DAAM EC2 Deploy

Key:
contents of ~/.ssh/daam_ec2_deploy.pub
```

For a deployment server that only needs to clone and pull code, **read-only access is normally sufficient**.

Do not enable write access unless the server genuinely needs to push to the repository.

---

## 4.3 Test the deploy key locally

Run:

```bash
ssh -T -i ~/.ssh/daam_ec2_deploy git@github.com
```

A successful result looks similar to:

```text
Hi nuriyevn/daam-dis! You've successfully authenticated,
but GitHub does not provide shell access.
```

This confirms that GitHub recognizes the deploy key.

# 5. Protect the private deploy key

The Terraform configuration receives the private deploy key through:

```hcl
github_deploy_key = <<EOF
-----BEGIN OPENSSH PRIVATE KEY-----
...
-----END OPENSSH PRIVATE KEY-----
EOF
```

The variable is marked sensitive in Terraform.

However, `sensitive = true` only prevents the value from being displayed normally in Terraform output.

The private key can still exist in Terraform state.

Therefore:

**Treat Terraform state as sensitive.**

Never commit:

```text
terraform.tfstate
terraform.tfstate.backup
terraform.tfvars
```

The `.gitignore` should include at least:

```gitignore
.terraform/
*.tfstate
*.tfstate.*
*.tfvars
*.tfvars.json
*.pem
crash.log
crash.*.log
```

For a team or production environment, use a secure remote Terraform backend and consider storing the GitHub deploy key in AWS Secrets Manager or SSM Parameter Store instead of placing the private key directly in Terraform variables/state.

# 6. Configure Terraform variables

Create:

```text
terraform/terraform.tfvars
```

Example:

```hcl
aws_region    = "ap-south-1"
instance_type = "t3.micro"
key_name      = "daam-dis-terraform"
ssh_cidr      = "0.0.0.0/0"

github_deploy_key = <<EOF
-----BEGIN OPENSSH PRIVATE KEY-----
YOUR_PRIVATE_DEPLOY_KEY
-----END OPENSSH PRIVATE KEY-----
EOF
```

Replace `YOUR_PRIVATE_DEPLOY_KEY` with the contents of:

```text
~/.ssh/daam_ec2_deploy
```

Do not use the `.pub` file here.

The Terraform variable must contain the **private** key.

# 7. SSH access configuration

The Terraform configuration creates an EC2 SSH key pair.

The generated private key is saved locally as:

```text
daam-dis-terraform.pem
```

Protect it:

```bash
chmod 600 daam-dis-terraform.pem
```

On Windows, use the appropriate file permissions or keep the file in a protected location.

The EC2 username for Amazon Linux is:

```text
ec2-user
```

After deployment, SSH access is:

```bash
ssh -i daam-dis-terraform.pem ec2-user@<ELASTIC_IP>
```

# 10. Review the deployment

Run:

```bash
terraform plan
```

Review the resources carefully.

The plan should show the EC2 instance, networking/security resources, key resources, and Elastic IP association.

Do not blindly apply an unexpected plan.

---

# 11. Deploy

Run:

```bash
terraform apply
```

Terraform will ask for confirmation.

Enter:

```text
yes
```

Terraform will then:

1. create or use the required AWS networking resources,
2. create the EC2 key pair,
3. create the security group,
4. launch the EC2 instance,
5. allocate/associate the Elastic IP,
6. install the required software,
7. configure the GitHub SSH deploy key,
8. clone the `codebase` branch,
9. run the DAAM setup script,
10. enable/start Nginx.

# 18. Updating application code

Terraform's `user_data` is intended primarily for initial EC2 provisioning.

After the server already exists, pushing a new application commit does **not** automatically cause Terraform to clone the new code.

For a manual update:

```bash
cd ~/daam
git pull origin codebase
```

Then rebuild/restart the application as appropriate.

For example, after a frontend source change:

```bash
npm run build:frontend
```

A future CI/CD workflow should automate this process using GitHub Actions.

---

# 19. When Terraform needs to be run again

Use Terraform when infrastructure changes.

Examples:

- changing EC2 instance type,
- changing disk size,
- changing security-group rules,
- changing the Elastic IP configuration,
- changing bootstrap/server configuration,
- changing AWS resources.

Do **not** run Terraform merely because a normal application file changed.

For normal application changes:

```text
Git commit
    ↓
Git push
    ↓
deployment / CI
    ↓
server update
```

# 20. Replacing the EC2 instance

If the instance must be recreated deliberately:

```bash
terraform apply "-replace=aws_instance.daam"
```

This causes Terraform to destroy and recreate the EC2 instance.

The Elastic IP is associated with the newly created instance by Terraform.

**Warning:** recreating the instance destroys data stored only on that instance. Application state that must survive instance replacement should live in external persistent services/storage.

Test GitHub authentication:

```bash
ssh -T git@github.com
```

Test repository access:

```bash
git ls-remote git@github.com:nuriyevn/daam-dis.git
```

Check the deploy key in:

```text
GitHub repository
→ Settings
→ Deploy keys
```

Make sure the public key corresponds to the private key supplied to Terraform.

---

## EC2 bootstrap failed

Check cloud-init:

```bash
sudo cloud-init status
```

View the log:

```bash
sudo tail -200 /var/log/cloud-init-output.log
```

This is usually the first place to investigate installation or Git clone failures.

---

## Frontend cannot resolve an imported file

For example:

```text
Failed to resolve import "../img/background.jpg"
```

Check:

```bash
find frontend/src -type f | sort
```

The imported file must actually exist.

For example:

```jsx
import backgroundImage from '../img/background.jpg';
```

requires:

```text
frontend/src/img/background.jpg
```

---

Check:

```bash
sudo systemctl status nginx
```

```bash
sudo systemctl restart nginx
```

Check configuration:

```bash
sudo nginx -t
```

# 24. Security considerations

The current development configuration allows SSH from:

```text
0.0.0.0/0
```

This means SSH is reachable from the Internet.

For production, change:

```hcl
ssh_cidr = "0.0.0.0/0"
```

to the administrator's trusted public IP/CIDR whenever possible.

Also consider:

- GitHub deploy key should be read-only.
- Terraform state should use a protected remote backend.
- Secrets should preferably be stored in AWS Secrets Manager or SSM Parameter Store.
- HTTPS should be enabled.
- Application services should run under appropriate system users.
- Production processes should be managed by systemd or another process supervisor.
- Nginx should proxy public traffic to the internal frontend/backend ports.
- Do not expose ports 3000/3001 publicly unless there is a specific reason.

# 25. Recommended production architecture

The current Terraform deployment establishes the infrastructure and initial application deployment.

The intended production architecture is:

```text
                    Internet
                       |
                       | 80 / 443
                       v
                    Nginx
                    /    \
                   /      \
                  v        v
             Frontend     /api
               :3000        |
                             v
                          Backend
                           :3001
```

The EC2 security group should expose the public HTTP/HTTPS entry points while the application ports remain internal.

A future CI/CD flow should be:

```text
Developer
    |
    | git push
    v
GitHub
    |
    v
GitHub Actions
    |
    | deploy
    v
EC2
    |
    +--> frontend build
    |
    +--> backend restart
```

Terraform remains responsible for infrastructure and server provisioning; CI/CD becomes responsible for application releases.

# 28. Summary

A new developer should be able to deploy DAAM with:

```bash
cd terraform

terraform init
terraform fmt
terraform validate
terraform plan
terraform apply
```

provided that:

1. AWS credentials are configured.
2. A GitHub Deploy Key has been generated.
3. The public Deploy Key has been added to `nuriyevn/daam-dis`.
4. The private Deploy Key is supplied through `github_deploy_key` in the local, uncommitted `terraform.tfvars`.
5. The required Terraform variables are configured.

The EC2 bootstrap then installs the required software and clones the private repository's `codebase` branch.
